# CaliChat — Hand-over for the next developer / AI assistant

> Paste this file into a new chat (or give it to a new developer) together with the project folder. It tells you what this project is, how it works, what is done, what is not, and the traps already hit. Read sections 1–3 first. Secrets are NOT in this file or in the repo (`.env` is excluded).

## 1. What this is
**CaliChat** is a **multi-tenant agentic conversational AI platform** (SaaS) for businesses in Sri Lanka (customers write in **English, Sinhala, Tamil**). It answers customers on **WhatsApp (Meta Cloud API or Twilio), Messenger and Instagram DMs**, fetches live data (products, stock, orders…) from each business's own ERP/CRM/store via configurable REST "tools" **or from CaliChat's own built-in Store + CRM (Phase 1, below)**, sends **WhatsApp templates and automatic follow-ups**, and can **autonomously create/update/cancel orders and record/confirm leads** — safely — while humans can take over any chat.

Roles: **super admin** (platform operator) → **tenants** (businesses) → **owner** / **agent** users. Everything tenant-owned carries `tenant_id`.

Owner's preferences learned in the conversation: **light theme only** (no automatic dark mode); thorough, production-minded work; wants artifacts/documents for reports and manuals; **MFA deliberately deferred** ("leave MFA for now"); wants honest reporting of what is/was not tested; hates unexplained changes. Product name **CaliChat**, accent colour indigo `#5B5BF0`, UI modelled on the owner's "Calimax ERP" dashboard screenshot (sidebar, rounded cards, big numbers).

## 2. Stack and hard constraints
- **PHP 8.0-compatible** (XAMPP on Windows; do NOT use 8.1+ syntax such as enums, readonly, `new` in initialisers, first-class callable syntax). Procedural-ish PHP with namespaced services (`CaliChat\…`, PSR-4-style autoloader in `config/bootstrap.php`; no Composer needed).
- **MariaDB 10.4 / InnoDB utf8mb4**. DB name **`calichat_ai`** (the database `calichat` on the dev machine belongs to a different project: never touch it). Times stored **UTC**; shown in the tenant's timezone (`local_dt()`).
- **Vanilla HTML/CSS/JS**, no build step. Strict CSP (`script-src 'self'`): **no inline scripts or inline event handlers**; styles may be inline.
- **Gemini API** (REST). Primary model `gemini-3.1-flash-lite`; fallback `gemini-3.5-flash-lite` (faster, ~2 s vs 8 s in one test; consider making it primary after quality testing). Embeddings `gemini-embedding-001` (256 dims). **Model availability changes without notice** (a previous fallback `gemini-2.5-flash-lite` was retired): list models with the key before assuming.
- Optional **TencentDB Agent Memory** sidecar (https://github.com/TencentCloud/TencentDB-Agent-Memory, MIT, Node ≥ 22). Adapter exists (`src/Memory/TencentMemory.php`) with circuit breaker + fallback to built-in MySQL memory; **never verified against a live service**; tool names/arguments are configurable guesses (`cli/verify_tencent.php` lists real ones).

## 4. Architecture in one page
```
Meta webhook ─┐                                   ┌─ /webhook/{channel_key}  per-channel (own Meta app, Twilio)
Twilio form  ─┼─► verify signature ─► queue ─►200 │─ /webhook/meta           platform Meta app (one URL, routed by page/IG/phone-number id)
              │   inbound_events (durable)
              ▼

   ─► Chat::conversation/contact (per-contact DB lock) ─► [voice/image → text via Gemini multimodal]
   ─► Chat::respond ─► Agent::reply (Gemini function-calling loop, ≤5 steps, 28 s deadline)
```

## 5. Invariants — do not break
1. **Every tenant query is scoped by `tenant_id` taken from the session**, never from request input. Add a test to `tests/run.php` for each new endpoint that takes an id.
2. **Write tools are gated server-side** (`ToolRunner::writeGate`): first call = preview (stored with args hash), real call only with `customer_confirmed=true`, identical args, a NEW customer message after the preview, once only, ≤6 writes/chat/hour (`WRITE_LIMIT_PER_HOUR`), optional `requires_approval` → `pending_actions`. Playground may run writes (checkbox) but `tools/test` (UI test panel) is GET-only.
3. **Claim check** (`Agent::unsupportedClaim`): the AI must not cite ORD-/LEAD-/ENQ-… references no tool returned, nor claim "done" while a preview is open and no write ran; one corrective retry (with the exact tool + args from the stored preview), then block + handoff. This exists because the model once invented "LEAD-8842".
4. Don't put imitable "lookup" text into the model's own past turns (it copies the format and hallucinates). Past tool results go in the system prompt block "RESULTS OF EARLIER TOOL CALLS".
5. Write-tool responses are NOT unwrapped (`response_path` empty) so the system's `message` and flags (`duplicate`, `idempotent_replay`) reach the AI; read tools use `response_path=data`.
6. Tool response fields are **default-deny** (`response_fields` or explicit `expose_all`); secret-named keys and Luhn-valid card numbers are always redacted; customer identity comes from `contact.phone` parameters (never AI-supplied).
7. Webhooks: verify signature → `INSERT IGNORE` into `inbound_events` (unique `channel_id,provider_id`) → 200 fast. Processing is at-least-once with per-sender ordering.
8. Secrets (channel tokens, connector secrets, tenant Gemini keys, platform Meta secret) are AES-256-GCM encrypted; never echo them back to the UI.
9. **Store/CRM:** every money/stock/order rule lives in `Store.php`, not in pages or the API. AI-placed orders above the tenant's `store_max_total` are refused (staff may exceed). An order is visible or changeable through the API only with its own phone; the tenant comes from the token. `cost_price` is in API output on purpose and is kept from the AI by the tool's `response_fields` allow-list: never add it to a tool.
10. **Follow-ups never bypass WhatsApp rules:** free text only inside 24 h of the customer's last message, otherwise an *approved* template; marketing-type triggers (`chat_idle`, `review_request`) and marketing templates need `consent_status='opted_in'`; quiet hours (tenant setting, default 21:00-08:00) postpone sending; state is re-checked at send time (order cancelled, customer wrote again, chat taken over); one run per (automation, subject) through a UNIQUE key; every outcome is stored with a readable reason.
11. **Order extraction:** the AI extracts details; the SERVER validates. `Store::check()` (tool `check_order`) is a dry run that reports every problem and missing field; `create_order` still goes through the preview, customer reply, confirmed-call gate. When the same preview is asked for again after the customer replied, the gate keeps the original preview and nudges the model to make the confirmed call (do not "simplify" this: re-recording the preview resets the confirmation). Saved customer details go to the prompt as UNVERIFIED data; the AI must offer them, not use them silently. `no_confirm` tools (`save_customer_details`) may only store the customer's own details, never money, stock or orders.
12. **Payments:** the AI never marks an order paid. A slip image only moves an order to `review` (a person verifies, `Slips::decide`). Orders with `payment_status='review'` still need a human. Slip files are served only through `api/slips/file` (session + tenant check).
13. **Billing gate:** `Chat::respond` holds the AI for `billing_status` lapsed/cancelled (`Billing::blocked`). Existing tenants are grandfathered: `active` with no end date. Do not add a payment gateway behaviour that marks invoices paid automatically without a signature check.
14. **Capabilities:** owners and the platform admin have every capability; members use `users.permissions` (JSON list) or the defaults in `Perms::CAPS`. Gate pages in `index.php` (`Perms::pageCap`), writes with `Auth::requireCan`, display of numbers with `phone_view()`, and the inbox API with `$mayAccess` (not `inbox_all` = own plus unassigned chats). New pages need an entry in `Perms::PAGES` and their writes need `requireCan`.
15. **Follow-ups never message people outside the rules** (see 10) and SMS fallback honours marketing consent too.
16. Gemini quirks: keep raw `parts` incl. `thoughtSignature` inside the tool loop; echo `functionCall.id` in `functionResponse`; **an empty `args` `{}` decodes to `[]` in PHP — re-encode as object** (`Agent::normalizeParts`); thinking tokens count against `maxOutputTokens` (default 4096, auto-doubles once).

## 8. Traps already hit (save yourself the time)
- **Editing on Windows:** PowerShell `Set-Content -Encoding utf8` adds a BOM (broke a migration; `Migrator` now strips it). Source files mix LF/CRLF — string-replace tools may "not find" text; use exact-match edits or normalise. Bash heredocs once truncated a SQL file: use file-write tools for big files.
- **.htaccess deny rules must only apply to paths that exist on disk** (`/app/...` URLs are routes). The PHP built-in server ignores `.htaccess`, so tests cannot catch this — `apache_check.sh`-style curl checks against real Apache were used.
- PHP built-in server reports a different `SCRIPT_NAME` → `base_path()` returns '' for `cli-server`.
- Live-test scripts must use **unique message ids** per run (events are keyed by channel+provider id) and filter by channel.
- The dev MariaDB once had corrupted Aria system tables (root login refused); repaired with `aria_chk` (backup of the folder was kept). Unrelated to CaliChat but explains odd history.
- Twilio signature = HMAC-SHA1(authToken, full URL + sorted params). Behind ngrok the URL differs from `APP_URL`; `Twilio::candidateUrls` tries the configured and the request-derived URL.
- Playground/test conversations (`conversations.is_test=1`) are excluded from quotas, dashboards and inbox; their token use is tracked separately (`test_tokens`).
- **Live Gemini found two real problems the unit tests did not** (both fixed): the model sometimes adds an optional field (such as `customer_name`) when confirming, which the identical-args gate refuses, so the error now returns the exact details the customer saw and the retry succeeds; and multi-word product searches ("black baseball cap") must match word by word, not as one phrase. Re-run `php tests/e2e/store_e2e.php` after changing prompts, tools or the gate.
- **Do not write patch scripts with backslashes in PHP double-quoted strings** (`\e` is the ESC character, `\\` may be collapsed by tooling): use the edit tool, single-quoted strings or `chr(92)`. Long shell heredocs with quotes fail on this machine: write files with the file tool.
- Live Gemini runs hit the free-tier limit (15 requests/minute) when run back to back; that shows as HTTP 429 inside the AI reply, not as a product bug. Production needs a paid key.
- Dates in tests: appointments and slots depend on "today"; the tests compute open weekdays dynamically (Sunday is closed by default).
- Template tests share state through the Graph stub (`cc_stub_templates.json` in the temp dir): use unique template names per test. In PHP tests, `$a + $b` keeps `$a`'s values: use `array_merge` to override.
- **Windows drops empty environment variables** passed to a child process, so `GEMINI_API_KEY=''` does not stop a spawned test server from reading the real key in `.env` (the tests once called the real Gemini this way). Use the explicit kill switch `GEMINI_DISABLED=1` (`Tenant::geminiKey`). `STORAGE_PATH` points logos/cards at a throw-away folder in tests.
- **On the dev MariaDB (10.4.32, XAMPP) `SHOW COLUMNS FROM inbound_events` crashes the server** (silently, no log line; it then also dies while loading `ib_buffer_pool`, which was renamed to `ib_buffer_pool.bak` to start it again). Read column definitions from `database/migrations` instead of `SHOW COLUMNS`/`DESCRIBE` on that table. Restart: `mysqld.exe --defaults-file=C:\xampp\mysql\bin\my.ini --standalone`.
- A cancelled-order / "Cancel" button must not be named just "Cancel": `Chat::consentKeyword` treats a typed "cancel" as STOP. Taps bypass it (`reply_id`), and the typed fallback prompt says "No".
- `ToolRunner` caches GET results (`tool_cache`) keyed by URL + contact binding; idempotency keys include a 10-minute bucket so retries dedupe but deliberate repeats don't.
